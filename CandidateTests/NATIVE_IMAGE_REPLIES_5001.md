## 这次生图为什么空白

已检查的 OpenRouter 日志显示：上游 HTTP 200，正常完成，生成图片 1 张；
7,062 个输出 token 中有 7,024 个属于图片。调用客户端是 4999。
5000 仍使用相同的 Chat Completions 接收代码，只读取文字而忽略 `delta.images`。

原请求未启用输入/输出日志，因此旧图字节不能从该日志取回。本次修复让后续
请求能正确接收图片，无法恢复那一次已经丢失的图片。

## 已实现的修复

- 普通聊天和带工具的聊天都读取 `delta.images[].image_url.url` 的内嵌 base64
  图片，同时接受最终 `message.images` 形态；保留原始格式/字节，同一流中的
  重复最终图片不会重复保存。
- OpenRouter 图像输出模型按能力传递图文输出类型；自定义 `modalities` 优先。
  请求等待上限为 300 秒，并显示“等待图文回复”。Responses API 明确发出
  生图开始事件时显示“正在生成图片”，不编造百分比或计时进度。
- 图片走现有附件保存和显示流程。关闭流式文字显示时，状态和图片仍及时送达。
  纯文字答案会移除图片等待提示；先出图再继续工具调用，仍保留已经出图的状态。
  失败和取消会结束等待状态。
- 用量统计和进度事件不再单独算作成功回复。损坏数据、保存失败和明确的
  Chat Completions 流错误都会报告错误。
- 历史图片回传规则沿用现有设置。生成图和搜索得到的图都属于普通图片附件；
  是否再次发送取决于“持续发送历史图片”、图片数量/折叠状态和当前上下文范围。

协议依据：OpenRouter 自己的 SDK 接收器也读取同一 `delta.images` 字段：
[OpenRouter SDK 接收实现](https://github.com/OpenRouterTeam/ai-sdk-provider/blob/main/src/chat/index.ts)

本次支持原生聊天返回的内嵌 base64 图片。意外返回远程图片 URL 时会明确报错，
不会静默丢弃。直接使用 Gemini 接口的原生生图接收属于另一条链路，不在本次
OpenRouter 修复范围内。
