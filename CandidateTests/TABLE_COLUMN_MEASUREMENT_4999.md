## 单一产品改动

`MarkdownTableBlock.measuredColumnWidths` 原先测量每列表头及全部有效单元格，最后返回 `min(max(ceil(widest) + 28, 96), 260)`。现在当 `ceil(widest) + 28 >= 260` 时停止该列后续单元格测宽，返回规则保持不变。padding 和最大列宽提为函数内常量，让停止条件与最终钳制共用参数。

对于正常有限的测量宽度，`widest` 经 `max` 单调不减。停止条件成立后，后续单元格无法改变最终的 260 pt 列宽；未达到上限的列继续完整测量。表头已经达到上限时可跳过正文测宽。每次流式内容更新仍重新计算当前表格，没有跨更新复用状态。

所有表格行、单元格仍按原来的 Grid 构建与排版。4998 的自然高度约束、字体、取整、96–260 pt 宽度范围、换行、单元格样式、菜单及横向滚动原样保留。产品变更只有此 Swift 文件和主程序/扩展的 4999 构建号。

## 后续用户反馈：进入响应仍待改善

用户试用后回报“感觉没有太大的改善”，并明确慢在点进窗口时“不会马上响应”。这表示 4999 未带来明确可感知的进入提速；不是对列宽等价测试的否定，也没有新证据表明原高度问题复发。当前不要继续叠加表格测宽小修。

下一轮关注点击到首次可见响应，而不是只看关闭动画总时长。4998 旧日志从列表触觉反馈之后才开始计时，不能覆盖完整触摸响应；4999 的最新耗时尚未录制。应使用当前版本的匹配轻/重窗口，区分回调开始、触觉反馈、选中发布、内容准备、首次布局、关闭请求和驱动首个实际回调。各自耗时不要相加成屏幕呈现延迟；现有工具未提供显示器实际首帧证据。

只读复核还发现普通关闭可能触发自身的重新接续：RootView.swift:2008 对所有语义关闭且 detached 活跃的情况调用 external close 路径；2496 当前关闭任务自身发布 false 也符合该条件。2456 取消旧驱动、2467 重启，551 开始时间与初速度随之重置。4998 四次日志均有对应 REJOIN，但第二段约 550 ms 不是可以全部省去的额外等待，也未证明它造成此次用户感知的最初延迟。

诊断需要同时记录当前关闭目标、sequence、detached 状态、真实 progress，以及语义关闭任务开始/等待结束/发布前后。现有 semantic 日志读取 drawerDragProgress（此时被置 nil）得到的 0 不代表视觉已经关闭。目标是判断同一关闭是否被多余地重新启动，保留外部关闭、反转与手势接管的实际保护。

若首帧前主要耗时是内容准备，再依据占比选择：减少同时创建的表格子视图、合并重复准备、将确认可后台执行的纯计算移出主线程。当前完整 Grid 和真实底部就绪相互关联，不能直接换 LazyVGrid 或删除就绪条件；需要独立布局与底部实验。本轮仅记录反馈和诊断计划，没有修改产品、构建、安装或重新启动手机。
